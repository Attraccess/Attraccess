# Architecture

Attraccess is structured as an NX monorepo containing multiple applications and shared libraries. This page provides an overview of the project organization.

## Monorepo Structure

```
Attraccess/
├── apps/
│   ├── api/                  # NestJS backend
│   ├── frontend/             # React frontend
│   └── attractap/
│       └── firmware/         # Attractap RFID reader firmware
├── libs/
│   ├── api-client/           # Generated OpenAPI client
│   ├── react-query-client/   # Generated TanStack Query hooks
│   ├── application-models/   # Neutral records and shared values
│   ├── database-entities/    # SQLite TypeORM schema definitions
│   ├── shared/               # Shared types and utilities
│   ├── plugins-backend-sdk/  # Plugin SDK for backend extensions
│   ├── plugins-frontend-sdk/ # Plugin SDK for frontend extensions
│   ├── plugins-frontend-ui/  # Shared UI components for plugins
│   └── env/                  # Environment configuration
└── storage/                  # SQLite database files (runtime)
```

## Applications

### Backend (`apps/api`)

The backend is a NestJS application that provides the REST API. It is organized into feature modules:

| Module             | Description                           |
| ------------------ | ------------------------------------- |
| **resources**      | Resource management (machines, doors) |
| **users-and-auth** | User accounts, authentication, SSO    |
| **settings**       | System configuration                  |
| **attractap**      | RFID reader communication             |
| **billing**        | Usage-based billing                   |
| **mqtt**           | MQTT broker integration               |
| **projects**       | Project management                    |
| **plugins**        | Plugin loading and management         |

### Frontend (`apps/frontend`)

The frontend is a React application built with:

- **HeroUI** – Component library for the user interface
- **TanStack Query** – Data fetching and caching
- **React Router** – Client-side routing
- **Vite** – Build tool and development server

The Vite development server proxies all `/api` requests to the backend, so the frontend always communicates through the same origin.

### Attractap Firmware (`apps/attractap/firmware`)

Firmware for the ESP32-based Attractap RFID card reader hardware. This is a separate embedded project.

## Libraries

### Generated Libraries

These libraries are auto-generated from the backend's OpenAPI specification and should not be edited manually:

| Library                | Description                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------- |
| **api-client**         | TypeScript HTTP client generated from the Swagger/OpenAPI spec (`Api.ts`)           |
| **react-query-client** | TanStack Query hooks generated from the API spec (`schemas.gen.ts`, `types.gen.ts`) |

After making API changes, regenerate these libraries to keep them in sync.

### Shared Libraries

| Library                | Description                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------ |
| **application-models** | Engine-independent records, enums and pure shared rules                              |
| **database-entities**  | SQLite schema classes and released migration compatibility; implementation code only |
| **shared**             | Types, interfaces, and utility functions used across apps                            |
| **env**                | Environment variable handling and configuration                                      |

### Plugin SDKs

| Library                  | Description                                   |
| ------------------------ | --------------------------------------------- |
| **plugins-backend-sdk**  | SDK for developing backend plugin extensions  |
| **plugins-frontend-sdk** | SDK for developing frontend plugin extensions |
| **plugins-frontend-ui**  | Reusable UI components for plugin frontends   |

## Database

SQLite is the only implemented relational backend. TypeORM is an implementation detail of its schema, migration and feature adapters. `DATABASE_TYPE=sqlite` is the default; unsupported selections fail before connections or plugin migrations. The database remains `<STORAGE_ROOT>/attraccess.sqlite` and released core migrations still run on startup before database-backed settings are read.

Application services depend on feature operation ports and plain records, not repositories or engine query objects. Nest modules select the implementations. Adapters own queries, database constraints and conditional writes; application services retain authorization, lifecycle transitions, calculations and external effects. Explicit REST and live-event response projections retain the public contract and exclude private fields without relying on ORM decorators.

| Owner                                    | Responsibility                                                                              |
| ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| `application-models`                     | Records and shared values without schema decorators                                         |
| Feature `persistence/port.ts`            | Named read/write operations and their neutral inputs/results                                |
| Feature `persistence/typeorm-adapter.ts` | SQLite queries, joins, ordering, persistence and plain record conversion                    |
| `database/sqlite/`                       | Connection/schema/migration track, transaction driver, engine errors and tooling            |
| `database/transaction-scope.ts`          | Parent transaction reuse, declared resource/account conflicts and post-commit notifications |
| Composition modules                      | Bind ports to implementations and transaction operations                                    |
| Backend SDK `/v2` and `/adapter`         | Separate plugin application capabilities from SQLite schema and adapter authoring           |

A parent `TransactionScope` is reused throughout one database phase. Nested work cannot open an independent commit or expand the parent's conflict set. The transaction callback runs once; database failures never automatically replay mail, device commands or other external work. Post-commit notifications run only after the outer commit. Existing invitation/email-change delivery remains inside its established transaction to preserve rollback behavior; moving it to an outbox requires a separate behavior change.

This refactor prepares replacement of persistence implementations. It does not implement PostgreSQL, transfer an existing database or establish multi-instance safety. SQLite's per-file write serialization is provider-owned. Process-local timers, queues, event delivery, flow execution and device ownership still need the coordination work in ATT-584, even with Valkey sessions. See [Adding a database backend](developer/adding-a-database-backend.md).

Unchanged consumers are intentional: released core/plugin migrations retain database-specific classes and SQL; native WAGO shell/firmware and Attractap hardware code keep their existing protocols; frontend/generated clients consume the same HTTP contract; RabbitMQ routes events without relational storage. Those are not additional backend implementations. Compatibility root SDK imports in historical migrations and implementation adapters do not authorize new application dependencies on TypeORM.

`database/conformance/persistence.spec.ts` runs reusable identity, accounting, lifecycle, audit, session and plugin suites. Every factory builds an isolated database from released migrations and removes all connections/files on close. Concurrent application tests enter barriers on distinct connections before either database phase starts; session barriers likewise precede atomic session operations. SQLite advertises `independentWriters: false`. Device and SMTP effects are simulated and counted; no physical device, payment provider or PostgreSQL behavior is inferred. Historical snapshots are constructed fixtures, not operator backups.

Process-local assumptions remain explicit: authorization caches and invalidation listeners, maintenance debouncing, resource transaction queues, flow executors, MQTT/WebSocket ownership, timers and in-memory notification streams are local to one API process. The neutral transaction contract permits independent resource scheduling, but SQLite still serializes writers. ATT-584 must implement database locks/pooling and cross-process event/device coordination before multiple API processes are supported.

## NestJS API Conventions

### Controller registration order is load-bearing

NestJS (via Express) matches routes in the order they are registered — **first registered wins**. A `:param` segment (e.g. `GET /users/:id`) matches _any_ single URL segment, including strings like `with-permission`. This creates a footgun:

```
// BROKEN — :id swallows every static path that follows
controllers: [UsersAdminController,    // has GET :id
               UserPermissionsController] // has GET with-permission ← unreachable!
```

`GET /users/with-permission` was removed with the legacy boolean-permission system in ATT-566. Role assignment queries now use `GET /users?roleId=...`; do not restore the removed route when adding role-related user list behavior.

**Rules to follow when adding or splitting a controller:**

1. **Within a single controller file**, declare all static-segment routes _before_ any `:param` route of the same HTTP method and same URL depth.
2. **In the `controllers: []` array of a module**, list controllers that have only static routes _before_ controllers that introduce `:param` routes at the same `@Controller(prefix)`.
3. When multiple controllers share the same `@Controller('path')` prefix (e.g. all the `@Controller('users')` controllers), a `:param` route in an earlier controller will shadow static routes in later ones.

An automated guard in `apps/api/src/route-shadow.spec.ts` enforces these rules in CI — any newly introduced shadow will cause the test suite to fail.
