# Architektur

Attraccess ist als NX-Monorepo aufgebaut und enthält mehrere Anwendungen sowie gemeinsam genutzte Bibliotheken. Diese Seite gibt einen Überblick über die Projektorganisation.

## Monorepo-Struktur

```
Attraccess/
├── apps/
│   ├── api/                  # NestJS-Backend
│   ├── frontend/             # React-Frontend
│   └── attractap/
│       └── firmware/         # Attractap RFID-Leser Firmware
├── libs/
│   ├── api-client/           # Generierter OpenAPI-Client
│   ├── react-query-client/   # Generierte TanStack-Query-Hooks
│   ├── application-models/   # Neutrale Datensätze und gemeinsame Werte
│   ├── database-entities/    # SQLite-TypeORM-Schemadefinitionen
│   ├── shared/               # Gemeinsame Typen und Hilfsfunktionen
│   ├── plugins-backend-sdk/  # Plugin-SDK für Backend-Erweiterungen
│   ├── plugins-frontend-sdk/ # Plugin-SDK für Frontend-Erweiterungen
│   ├── plugins-frontend-ui/  # Gemeinsame UI-Komponenten für Plugins
│   └── env/                  # Umgebungskonfiguration
└── storage/                  # SQLite-Datenbankdateien (Laufzeit)
```

## Anwendungen

### Backend (`apps/api`)

Das Backend ist eine NestJS-Anwendung, die die REST-API bereitstellt. Es ist in Feature-Module organisiert:

| Modul              | Beschreibung                            |
| ------------------ | --------------------------------------- |
| **resources**      | Ressourcenverwaltung (Maschinen, Türen) |
| **users-and-auth** | Benutzerkonten, Authentifizierung, SSO  |
| **settings**       | Systemkonfiguration                     |
| **attractap**      | RFID-Leser-Kommunikation                |
| **billing**        | Nutzungsbasierte Abrechnung             |
| **mqtt**           | MQTT-Broker-Integration                 |
| **projects**       | Projektverwaltung                       |
| **plugins**        | Plugin-Verwaltung und -Laden            |

### Frontend (`apps/frontend`)

Das Frontend ist eine React-Anwendung, die folgende Technologien nutzt:

- **HeroUI** – Komponentenbibliothek für die Benutzeroberfläche
- **TanStack Query** – Datenabruf und Caching
- **React Router** – Client-seitiges Routing
- **Vite** – Build-Tool und Entwicklungsserver

Der Vite-Entwicklungsserver leitet alle `/api`-Anfragen an das Backend weiter, sodass das Frontend immer über denselben Ursprung kommuniziert.

### Attractap Firmware (`apps/attractap/firmware`)

Firmware für die ESP32-basierte Attractap RFID-Kartenleser-Hardware. Dies ist ein eigenständiges Embedded-Projekt.

## Bibliotheken

### Generierte Bibliotheken

Diese Bibliotheken werden automatisch aus der OpenAPI-Spezifikation des Backends generiert und sollten nicht manuell bearbeitet werden:

| Bibliothek             | Beschreibung                                                                                 |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| **api-client**         | TypeScript-HTTP-Client, generiert aus der Swagger/OpenAPI-Spezifikation (`Api.ts`)           |
| **react-query-client** | TanStack-Query-Hooks, generiert aus der API-Spezifikation (`schemas.gen.ts`, `types.gen.ts`) |

Nach Änderungen an der API müssen diese Bibliotheken neu generiert werden, um sie synchron zu halten.

### Gemeinsame Bibliotheken

| Bibliothek             | Beschreibung                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------- |
| **application-models** | Datenbankunabhängige Datensätze, Enums und gemeinsame reine Regeln                              |
| **database-entities**  | SQLite-Schemaklassen und Kompatibilität veröffentlichter Migrationen; nur für Implementierungen |
| **shared**             | Typen, Interfaces und Hilfsfunktionen, die anwendungsübergreifend genutzt werden                |
| **env**                | Umgebungsvariablen-Verwaltung und Konfiguration                                                 |

### Plugin-SDKs

| Bibliothek               | Beschreibung                                          |
| ------------------------ | ----------------------------------------------------- |
| **plugins-backend-sdk**  | SDK zur Entwicklung von Backend-Plugin-Erweiterungen  |
| **plugins-frontend-sdk** | SDK zur Entwicklung von Frontend-Plugin-Erweiterungen |
| **plugins-frontend-ui**  | Wiederverwendbare UI-Komponenten für Plugin-Frontends |

## Datenbank

SQLite ist das einzige implementierte relationale Backend. TypeORM bleibt ein Implementierungsdetail der Schema-, Migrations- und Fachadapter. `DATABASE_TYPE=sqlite` ist der Standard. Nicht unterstützte Werte stoppen den Start vor Verbindungen oder Plugin-Migrationen. Die Datei bleibt `<STORAGE_ROOT>/attraccess.sqlite`. Veröffentlichte Kernmigrationen laufen weiterhin vor dem Lesen datenbankbasierter Einstellungen.

Anwendungsdienste verwenden fachliche Operationen und normale Datensätze statt Repositories oder Datenbankabfrageobjekten. Nest-Module wählen Implementierungen aus. Adapter besitzen Abfragen, Datenbankconstraints und bedingte Schreibvorgänge. Berechtigungen, Zustandsübergänge, Berechnungen und externe Wirkungen bleiben in den Anwendungsdiensten. Ausdrückliche REST- und Live-Antwortprojektionen erhalten den öffentlichen Vertrag und entfernen private Felder unabhängig von ORM-Dekoratoren.

| Zuständigkeit                               | Aufgabe                                                                                     |
| ------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `application-models`                        | Datensätze und gemeinsame Werte ohne Schemadekoratoren                                      |
| Fachliches `persistence/port.ts`            | Benannte Lese- und Schreiboperationen mit neutralen Ein- und Ausgaben                       |
| Fachliches `persistence/typeorm-adapter.ts` | SQLite-Abfragen, Verknüpfungen, Reihenfolge, Speicherung und normale Datensätze             |
| `database/sqlite/`                          | Verbindung, Schema, Migrationen, Transaktionstreiber, Datenbankfehler und Werkzeuge         |
| `database/transaction-scope.ts`             | Gemeinsame Elterntransaktion, Ressourcen- und Kontenkonflikte und Meldungen nach dem Commit |
| Verdrahtungsmodule                          | Schnittstellen mit Implementierungen und Transaktionsoperationen verbinden                  |
| Backend-SDK `/v2` und `/adapter`            | Plugin-Anwendungsfähigkeiten von SQLite-Schema und Adaptercode trennen                      |

Innerhalb einer Datenbankphase wird derselbe `TransactionScope` weitergereicht. Verschachtelte Arbeit führt keinen eigenen Commit aus und erweitert den Konfliktbereich nicht. Der Transaktionscallback läuft einmal; Datenbankfehler wiederholen niemals automatisch E-Mails, Gerätebefehle oder andere externe Arbeit. Meldungen nach dem Commit laufen erst nach dem äußeren Commit. Der bestehende Mailversand bei Einladungen und E-Mail-Änderungen bleibt zur Erhaltung des Rücknahmeverhaltens innerhalb der Transaktion. Eine Outbox wäre eine separate Verhaltensänderung.

Der Umbau bereitet den Austausch der Persistenzimplementierungen vor. PostgreSQL, Datenübernahme und sicherer Mehrinstanzbetrieb sind damit nicht implementiert. SQLite serialisiert Schreibvorgänge innerhalb seiner Implementierung pro Datei. Lokale Timer, Warteschlangen, Ereignisverteilung, Flow-Ausführung und Gerätezuständigkeiten benötigen in ATT-584 weitere Koordination, auch mit Valkey-Sitzungen. Siehe [Ein Datenbank-Backend ergänzen](developer/adding-a-database-backend.md).

### Zuständigkeit der Persistenz nach Pfad

Alle Pfade sind relativ zum Repository. Das Nest-Modul jedes Fachbereichs bindet dessen Port und Transaktionstoken; fachliche Regeln bleiben in den Diensten des Bereichs. Unveränderte Verbraucher sind beabsichtigt: Veröffentlichte Kern-/Plugin-Migrationen behalten Engine-Klassen und SQL; native WAGO-Shell/Firmware und Attractap-Hardware behalten ihre Protokolle; Frontend und generierte Clients verwenden denselben HTTP-Vertrag; RabbitMQ leitet Ereignisse ohne relationale Tabellen weiter. Sie sind keine weiteren Backend-Implementierungen. Alte SDK-Importe in Migrationen und Adaptern erlauben keine neuen TypeORM-Abhängigkeiten in Anwendungsdiensten.

`database/conformance/persistence.spec.ts` führt wiederverwendbare Identitäts-, Buchungs-, Nutzungs-, Audit-, Session- und Plugin-Suites aus. Jede Factory erstellt eine isolierte Datenbank mit veröffentlichten Migrationen und entfernt beim Schließen alle Verbindungen und Dateien. Überlappende Aufrufe erreichen auf getrennten Verbindungen eine Barriere vor Beginn der Datenbankphase; Session-Barrieren liegen ebenfalls vor der atomaren Operation. SQLite deklariert `independentWriters: false`. Geräte-/SMTP-Effekte sind simuliert und werden gezählt; daraus folgt kein Beweis für Hardware, Zahlungsanbieter oder PostgreSQL. Historische Snapshots sind konstruierte Fixtures, keine Betreiber-Backups.

Prozesslokal bleiben Autorisierungscaches und deren Invalidierung, Wartungs-Debouncing, Transaktionswarteschlangen, Flow-Ausführung, MQTT-/WebSocket-Besitz, Timer und Benachrichtigungsströme. Der neutrale Transaktionsvertrag erlaubt unabhängige Ressourcen; SQLite serialisiert weiterhin Schreibzugriffe. ATT-584 muss Datenbanksperren/Pooling und prozessübergreifende Ereignis-/Gerätekoordination bereitstellen, bevor mehrere API-Prozesse unterstützt werden.

## Authentifizierung

Die Authentifizierung erfolgt über **Session-Cookies**. Das System unterstützt:

- Anmeldung mit Benutzername/Passwort
- SSO über OpenID Connect (OIDC)
- SSO über SAML
- Zwei-Faktor-Authentifizierung (TOTP)
